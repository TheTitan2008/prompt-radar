1. PROJECT PURPOSE

Prompt Radar is an offline-first Python project for analyzing corporate AI-agent
usage logs at the level of real user tasks. The system reconstructs tasks from
chat/export data, extracts current user goals, classifies requests into known
business scenarios, discovers emerging request clusters, and estimates
potential economics of using AI agents.

The project is explicitly split into two hackathon tasks:

Task 1:
- understand what prompts/users/tasks exist in the dataset;
- group them into known themes, emerging themes and unresolved/noise;
- produce stable structured outputs and cluster-level summaries.

Task 2:
- estimate the economic effect of agent usage;
- compare cost of the platform/agent with value of saved labor time;
- provide management-ready outputs such as ROI, break-even, token cost and
  FTE-based value.

3. HIGH-LEVEL ARCHITECTURE

The project has these major layers:

3.1 Ingestion and security
- reads dataset.zip safely;
- validates manifest and all JSONL entities;
- protects against Zip Slip, nested archive abuse, path traversal and related
  import issues;
- verifies relationships between users, conversations, messages, runs, events
  and attachments.

3.2 Run reconstruction and preprocessing
- rebuilds task units around run_id;
- has fallback segmentation when run_id is absent or incomplete;
- extracts the active user goal from messages rather than using the entire chat
  blindly;
- routes each run into one of the processing modes:
  - direct
  - long-context
  - attachment/RAG

3.3 Attachments handling
- reads text, markdown, CSV, JSON, XLSX, PDF and DOCX;
- builds bounded textual representations for retrieval and task understanding;
- does not require OCR for the first version.

3.4 Embeddings and classification
- embeds requests with a pinned Qwen embedding model;
- matches tasks against 31 known business use cases and 8 draft categories;
- keeps known classification separate from residual discovery.

3.5 Clustering and emerging-theme discovery
- clusters residual tasks with HDBSCAN;
- extracts representatives and cluster fingerprints;
- supports local reviewed cluster naming/economic passports for immutable demo
  datasets;
- can optionally use external OpenAI-compatible enrichment for other datasets.

3.6 Economics
- calculates potential savings and cost at run, cluster and platform level;
- includes GPU amortization, licenses, optional support/development/electricity
  overhead and variable costs;
- reports ROI, break-even quality, token economics and FTE-based value.

3.7 Reporting
- writes machine-readable JSON/JSONL/CSV/Parquet/NPZ artifacts;
- writes human-readable Markdown reports;
- writes a self-contained HTML statistics report.

6. MODELS USED

6.1 Embedding model
- Model id: Qwen/Qwen3-Embedding-0.6B
- Revision:
  97b0c614be4d77ee51c0cef4e5f07c00f9eb65b3

What it does:
- converts each task/request into a vector embedding;
- supports matching to known scenarios and residual clustering;
- is not used as a chat/generative model.

6.2 External chat-style model path (optional)

The project can optionally call an OpenAI-compatible endpoint for cluster
enrichment on non-demo datasets. This is intended for Qwen or DeepSeek style
chat models exposed through an OpenAI-compatible API.

What it does when enabled:
- names a coherent emerging cluster;
- proposes manual steps and time ranges;
- writes a bounded structured response.

What it does not do:
- it does not decide wages;
- it does not directly compute economic value;
- it does not override strict local matching rules for the fixed demo dataset.

8. MATHEMATICAL AND ECONOMIC LOGIC

8.1 Fixed labor rate

The local labor-value calculations use:
- employee_cost_per_hour = 1500 RUB

This means:
- 25 RUB per minute

8.2 Platform cost components

The platform can include:
- GPU amortization
- licenses
- external API variable cost
- tools cost
- electricity
- support
- development
- shared tools monthly overhead

These are configured in:
- data/generated_800/economics_cost_config.json

8.3 Token economics

The final economics layer can now calculate:
- input tokens
- output tokens
- total tokens
- allocated cost per token
- full cost per token
- cost per 1k tokens
- cost per 1M tokens

8.4 FTE economics

The final economics layer can now calculate:
- saved FTE-months
- FTE-month value at a configured monthly cost
- B > A comparison, where:
  - A = platform/agent cost
  - B = value of saved labor time in FTE terms

The current config uses:
- average_fte_month_cost_rub = 400000

8.5 Important interpretation rule

Potential ROI is not the same as proven ROI.

Potential ROI means:
- the system estimates value under assumptions and available baselines.

Proven ROI requires:
- real prompt effort measurements;
- reviewed quality evidence;
- enough evaluated coverage.

Strategy B — demo-ready repository

issues.

16. DEMO NARRATIVE IN ONE PARAGRAPH

The system safely imports a chat/export dataset, reconstructs real user tasks,
understands what people ask the agent to do, matches known business scenarios,
discovers new coherent request groups with Qwen embeddings plus HDBSCAN,
attaches reviewed local answers for the fixed demo dataset without paying for
API calls, and then estimates token cost, labor savings, ROI and FTE value
with transparent assumptions and management-friendly reports.
